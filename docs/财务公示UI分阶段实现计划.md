# 财务公示 UI 分阶段实现计划

> 版本：v0.1
>
> 状态：Stage 1–7 已完成
>
> 参考：用户提供的“财务公示 / 账目公示”桌面端 UI 参考图

## 1. 目标与范围

为“猫猫手册”新增一个顶层“财务公示”模块，内部包含两个视图：

1. **账目公示**：默认视图，本次实现重点。
2. **价格参考**：第二视图，复用现有价格参考数据和展示逻辑。

整体目标是让访客能够快速理解收支概况、按月份和类别查账，并查看单条账目的公开详情，同时保持 Cats 现有的暖色档案风格。

本次第一版不做实时腾讯文档同步，采用站点内的静态规范化数据，由构建流程发布。

## 2. 参考图解读与冻结内容

参考图只用于确定 PRESENTATION，不作为真实数据来源。图中的示例猫名、金额、日期、凭证和事项不得直接写入网站。

### 2.1 桌面端目标结构

```text
财务公示页
├── 页面标题、说明、数据截止日期
├── 内部视图切换
│   ├── 账目公示（默认）
│   └── 价格参考
├── 收支摘要
│   ├── 现金收入
│   ├── 现金支出
│   └── 记录净额
├── 主体双栏
│   ├── 左侧：搜索、筛选、月份账目列表
│   └── 右侧：选中账目详情
└── 页脚说明
```

### 2.2 账目列表冻结结构

桌面端账目列表按月份分组，默认按日期从新到旧排列。每条记录至少展示：

```text
日期｜类型｜事项｜类别｜关联猫咪｜金额｜凭证
```

收入、支出、实物捐赠使用不同但克制的状态标签。金额使用正负方向和颜色辅助识别，但不能只依赖颜色表达含义。

右侧“账目详情”卡展示当前选中记录的完整公开字段。默认选中最新一条可公开展示的记录；如果没有选中记录，显示简短的引导状态。

### 2.3 移动端目标结构

移动端不压缩桌面表格，而是转换为单列档案记录：

```text
页面标题与截止日期
视图切换
收支摘要横向滚动或两列排列
搜索与筛选
月份分组
账目记录卡片
账目详情展开区或底部抽屉
```

桌面端右侧详情卡在移动端改为点击记录后展开，或使用底部抽屉。第一版不要求同时显示列表和详情双栏。

### 3.1 数据边界

- 两条 ¥0.00 记录是实物捐赠，不计入现金收入或现金余额。
- 一条只有日期和余额、没有事项和收支金额的记录属于占位/期初记录，不作为普通流水展示。
- `结余`可以转换为单条记录的收支净额，因为目前与 `收入 - 支出`一致。
- `余额`只有部分记录填写，且不能通过简单的时间累计完全对账，第一版不能将其作为权威账户余额。
- 页面应使用“记录净额”而不是“账户余额”，并显示“数据截止 2026-08-24”。
- “夏至”“小红猫”“斜眼狼儿子”“槿月”“食堂橘猫”暂未完成猫名映射，不能自动创建新档案；应使用“待核对”状态。
- “渣男”是“赫兹”的历史别名，应在规范化数据层处理，不在 UI 中作为新猫展示。

## 4. 目标数据契约

原始腾讯文档 CSV 只作为审计输入，不直接交给页面渲染。站点需要维护一份规范化的、可追溯的静态公示数据。

建议正式记录结构为：

```js
{
  id: 'finance-...',
  date: '2026-08-24',
  recordType: 'cash', // cash | in_kind | opening | review
  direction: 'income', // income | expense | none
  amount: 200,
  category: '捐赠收入',
  description: '规范化后的事项',
  relatedCats: ['猫名'],
  note: '允许公开的备注',
  evidence: null,
  source: {
    sheet: '公账收支表',
    sourceRow: 123,
    recordId: null,
  },
  visibility: 'public',
  reviewStatus: 'verified',
}
```

要求：

- 金额使用数字，显示时再格式化为人民币。
- `direction` 与 `amount` 分开保存，不把带符号字符串作为业务字段。
- `recordType` 单独区分现金、实物捐赠、期初记录和待核对记录。
- `relatedCats` 使用规范名称数组，保留无法映射的原始名称和待核对状态。
- 原始负责人、捐款昵称和未确认身份信息保留在内部审计层，不默认公开。
- `reportedBalance` 如果保留，只能作为原始字段或核验字段，不能直接替代 `balanceAfter`。
- 数据必须保留来源表、源行号；后续重新爬取时应尽量补回腾讯文档原始 `recordId`。

## 5. 分阶段实施

### Stage 0：冻结产品、数据和工作区边界（已完成）

**目标**：在写页面前固定真实数据口径和参考图中的布局关系。

**工作内容**：

- 记录当前工作区状态，保留用户已有的未提交改动。
- 确认财务模块命名为“财务公示”，默认子视图为“账目公示”。
- 确认“记录净额”不等于“账户余额”。
- 确认两条实物捐赠和一条占位记录的分类策略。
- 确认待映射猫名的展示方式。
- 冻结桌面端双栏和移动端单列的基本结构。

**完成标准**：数据字段、公开边界、页面层级没有待决的核心歧义。

冻结结果见：[财务公示 Stage 0 冻结记录](./财务公示Stage0冻结记录.md)。

### Stage 1：建立规范化财务数据层与校验器（已完成）

**目标**：让 UI 消费一份稳定、可追溯、可验证的数据，而不是直接读取原始 CSV。

**计划改动**：

- 新增站点拥有的规范化财务数据文件 `src/data/finance-snapshot.js`。
- 在 `src/data/index.ts` 中补充统一导出。
- 新增生成脚本 `scripts/generate-finance-data.mjs` 和校验脚本 `scripts/validate-finance-data.mjs`。

**校验项目**：

- 日期格式和时间范围；
- 金额、收支方向和 `结余` 一致性；
- 类别是否在允许枚举内；
- 现金、实物、期初和待核对记录是否分类正确；
- `id` 是否唯一；
- 重复候选是否只标记、不自动删除；
- 猫名映射和待核对名称；
- 隐私字段是否进入公开层；
- 来源表、源行号和原始记录追溯信息。

**完成标准**：校验器通过；能够生成收入、支出、记录净额和数据截止日期；不会把未核验余额作为公开余额。

### Stage 2：搭建财务公示页面壳和视图切换（已完成）

**目标**：先实现参考图的页面骨架，不急于加入全部筛选逻辑。

**计划改动**：

- 在当前侧边栏中将现有“价格参考”重新组织到“财务公示”模块下。
- 新增“账目公示 / 价格参考”内部视图切换。
- 在 `src/scripts/legacy-app.js` 中增加财务页面状态和渲染入口。
- 在 `src/styles/finance.css` 中新增 `.finance-*` 样式区域，并由页面入口引入。
- 保留现有 `priceSnapshot` 数据和价格参考核心逻辑，避免复制两份价格数据。

**完成标准**：

- 桌面端出现标题、说明、数据截止日期、两个内部视图和三张摘要卡；
- 账目公示为默认视图；
- 价格参考能够从财务模块进入，现有价格数据不丢失；
- 不影响首页、猫咪详情、物资、编年史和知识库。

### Stage 3：实现账目列表和基础筛选（已完成）

**目标**：完成参考图左侧的核心账目浏览体验。

**功能**：

- 按月份分组；
- 默认日期倒序；
- 搜索事项、类别和关联猫咪；
- 收入 / 支出 / 实物筛选；
- 类别筛选；
- 月份筛选；
- 最新优先、日期排序等排序方式；
- 分页或按月份折叠，避免一次渲染过多记录；
- 无结果、无凭证、待核对记录状态。

**完成标准**：列表数量和筛选结果与规范化数据一致；实物捐赠不进入现金收入/支出统计；占位记录不会伪装成普通流水。

### Stage 4：实现账目详情和凭证展示（已完成）

**目标**：完成参考图右侧“账目详情”卡，并建立公开字段边界。

**功能**：

- 点击列表记录更新右侧详情；
- 桌面端详情卡保持可见或 sticky；
- 移动端改为展开区域或底部抽屉；
- 展示日期、类型、类别、金额、事项、关联猫咪、公开备注；
- 有公开凭证时显示查看入口；
- 无凭证时显示短横线或“暂无凭证”；
- 待核对记录显示状态提示，不隐藏其待核对事实；
- 不展示负责人、昵称、原始 token 或原始内部字段。

**完成标准**：详情内容完全由选中记录驱动；不会把参考图中的示例凭证或示例猫名带入真实页面。

### Stage 5：整合价格参考第二视图（已完成）

**目标**：把现有价格参考作为财务公示的第二个稳定视图，而不是重做一套新表。

**工作内容**：

- 保留现有价格分类、搜索、排序和价格筛选；
- 调整页面标题和内部导航，使其与“财务公示”统一；
- 明确价格数据快照日期为 2026-08-12；
- 确保切换视图时财务筛选状态和价格筛选状态互不污染。

**完成标准**：两个视图视觉统一但信息结构清晰；价格参考仍能独立浏览，账目公示状态不会影响价格参考。

### Stage 6：完成移动端适配（已完成）

**目标**：按参考图的内容层级重排移动端，而不是简单缩小桌面布局。

**重点**：

- 720px 以下单列布局；
- 摘要卡横向滚动或两列布局；
- 搜索和筛选按钮保持足够点击区域；
- 账目记录使用卡片/行式结构，金额和类型优先；
- 详情使用展开区或底部抽屉；
- 凭证图片不撑破视口；
- 长事项和备注能够自然换行；
- 与现有移动端侧边栏展开、页面滚动和猫咪详情遮罩不冲突。

**完成标准**：719px 以下使用单列卡片式布局；静态断点检查确认无宽表强制布局；列表、筛选、详情和凭证样式具备移动端结构。

### Stage 7：视觉验收、数据验收和 Freeze（已完成）

**目标**：确认实现接近参考图，同时没有牺牲真实数据和可维护性。

**验收顺序**：

1. 桌面端粗布局：页面宽度、双栏比例、摘要卡和表格位置；
2. 信息层级：标题、金额、类型、事项、详情卡的视觉优先级；
3. 颜色、字体、边框、间距和装饰强度；
4. 筛选、排序、选中态、详情态和凭证态；
5. 移动端重排、滚动和触摸交互；
6. 空数据、待核对、实物捐赠和无凭证记录；
7. 构建和静态检查。

每轮截图对比最多记录 5 个差异，优先修复最大的 1–3 个问题；如果连续多轮效果不佳，先检查父容器、网格、视口、字体、`box-sizing` 和区块高度，再继续微调。

**技术验收**：

- `node --check` 检查新增或修改的 JavaScript；
- 财务数据校验器通过；
- `npm run build` 通过；
- `git diff --check` 通过；
- 桌面端真实浏览器验收，移动端完成 719px 断点 CSS 和结构检查；
- 核对构建产物没有引入原始隐私字段和不应公开的腾讯文档凭据。

## 6. 第一版明确不做

- 不接入腾讯文档实时 API；
- 不自动同步或自动覆盖站点数据；
- 不把未核验 `余额`设计成账户余额；
- 不自动删除重复记录；
- 不自动把待映射猫名创建为新档案；
- 不默认公开救助人、负责人和捐款昵称；
- 不首期加入复杂图表、预算预测、收支预警或权限系统；
- 不把后台 CMS 扩展成财务编辑后台。

## 7. 实施顺序与交付边界

实际实施时按以下顺序推进：

```text
Stage 0 数据/视觉 Freeze
        ↓
Stage 1 规范化数据 + 校验器
        ↓
Stage 2 财务页面壳 + 双视图
        ↓
Stage 3 账目列表 + 筛选
        ↓
Stage 4 详情 + 凭证
        ↓
Stage 5 价格参考整合
        ↓
Stage 6 移动端
        ↓
Stage 7 截图验收 + 构建 Freeze
```

每个阶段单独检查 diff 和运行结果，不在未确认的数据语义上继续叠加 UI。第一阶段真正进入代码时，应先从规范化数据和校验器开始，而不是先改现有详情窗或直接把 CSV 复制进页面。
